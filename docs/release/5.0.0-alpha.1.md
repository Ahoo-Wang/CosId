# CosId 5.0.0-alpha.1 (draft release notes)

> Draft for the GitHub pre-release `v5.0.0-alpha.1` (decision D33). Not published yet: the release is the user's call.

## No compatibility promise

`5.0.0-alpha.x` is a preview. The API, configuration, storage format and cosid-server HTTP API may change between alphas
and before GA, and no data migration is provided between alphas. Do not use it in production: stay on 4.x there.

`5.0.0-alpha.x` 是预览版，不做兼容性承诺。API、配置、存储格式和 cosid-server HTTP 接口在 alpha 之间以及 GA 之前都可能变化，
alpha 之间不提供数据迁移。不建议用于生产：生产环境请继续使用 4.x。

This release is a GitHub pre-release, and the Docker image is not tagged `latest`. The documentation site
[cosid.ahoo.me](https://cosid.ahoo.me/) now documents 5.0 (alpha); the 4.x documentation stays on the `4.x` branch:

## What changes in 5.0

CosId 5 is a full rewrite with no backward compatibility and no 4.x compatibility code (D1).

- **Uniqueness depends on no clock** (D22). A machine slot is leased as a time window; successive holders' windows never
  overlap, and the store itself keeps that rule. Clock skew, GC pauses and failovers cost availability, never
  uniqueness. The namespace `tolerance` (default 1s) only affects availability (D20). Generation stops when the lease
  is lost; there is no switch to keep going (D24).
- **One runtime** (D17, D18). Every strategy runs on one immutable `CosIdRuntime` holding one machine slot shared by all
  time-based generators. Spring Boot, cosid-server and plain Java start it the same way.
- **Strategies.** Snowflake with any `Layout` (ms or s, JS-safe 53 bits as a preset; the default layout and epoch are
  the 4.x ones, so ids continue after a migration, D16), short critical section on the hot path (D25); segments whose
  reservations size themselves to a time budget, gaps allowed and never a duplicate (D19); periodic segments per year,
  month or day (D5); the 80-bit CosId as `Layout.COSID_80` (D4). `IntegerIdGenerator`, `UncertaintyIdGenerator` and
  similar classes are gone; `IdGenerators` composes their behaviour (D9).
- **Stores: two primitives, one TCK.** JDBC (MySQL 8.4+, MariaDB 10.11+, PostgreSQL 15+, SQL Server 2019+, H2 2.x),
  Redis 7.0+ (Lettuce, no Spring dependency, `WAIT` auto, D6), MongoDB 6.0+ (D26), ZooKeeper 3.8+ (D27), and the
  remote store backed by cosid-server. Stores are declared once and mixed freely. Segment keys are sealed, never
  deleted online (D23).
- **cosid-server** serves leases and ranges; the id endpoints are optional; the HTTP API has no version prefix
  (`/ranges:reserve`, `/slots:*`, `/ids/*`); the 4.x v1/v2 APIs are removed (D8, D30).
- **Spring Boot:** one starter, `cosid-spring-boot-starter`; add the store artifacts you use. Feature variants are
  removed (D14).
- **Modules:** directory names without the `cosid-` prefix, artifactIds keep it (D2, D11); integrations split by
  third-party dependency with the 4.x coordinates (D29); sharding algorithms in `cosid-sharding` (D7); `cosid-core`
  ships a JPMS `module-info` exporting only its API packages (D12); no Lombok (D13).
- **Baseline:** Java 21, Spring Boot 4.0+, package `me.ahoo.cosid` (D3).

## Coordinates

Group `me.ahoo.cosid`, version `5.0.0-alpha.1`. Import the BOM and add the starter and the stores you use:

```kotlin
dependencies {
    implementation(platform("me.ahoo.cosid:cosid-bom:5.0.0-alpha.1"))
    implementation("me.ahoo.cosid:cosid-spring-boot-starter")
    implementation("me.ahoo.cosid:cosid-store-jdbc")   // or cosid-store-redis, -mongo, -zookeeper, -remote
}
```

```xml
<dependency>
    <groupId>me.ahoo.cosid</groupId>
    <artifactId>cosid-bom</artifactId>
    <version>5.0.0-alpha.1</version>
    <type>pom</type>
    <scope>import</scope>
</dependency>
```

Artifacts in the BOM: `cosid-core`, `cosid-store-jdbc`, `cosid-store-redis`, `cosid-store-mongo`,
`cosid-store-zookeeper`, `cosid-store-remote`, `cosid-store-tck`, `cosid-spring-boot-autoconfigure`,
`cosid-spring-boot-starter`, `cosid-jackson`, `cosid-mybatis`, `cosid-spring-data-jdbc`, `cosid-activiti`,
`cosid-flowable`, `cosid-axon`, `cosid-sharding`.

## Migrating from 4.x

4.x and 5.0 never run in one namespace. Two ways over, both with every 4.x instance stopped:

- The offline tool `cosid-migration.jar` (Java 21), attached to this release: plan (read-only), apply, verify, then
  convert the configuration. See `migration/README.md` and the migration guide
  (`documentation/docs/en/guide/migration/from-4x.md`).
- A stop-the-world manual migration without the tool (D32), for deployments where it applies: the
  "Stop-the-world migration without the tool" section of the same guide.

Since alphas carry no data migration between them, migrate a copy of the data, not production.

## Known issues

The release gate (D21: performance and features no worse than 4.x) **fails**:
[run 40623986450](https://github.com/Ahoo-Wang/CosId/actions/runs/40623986450) on `main` `a68a0191`, 4.1.0 and 5.x
alternating on the same runner, failing rows rerun once. 6 of the 8 groups have rows below 4.x. An alpha is not gated on
it (D33); RC and GA still are (D21). Rows that still fail after the rerun:

- **Codec:** radix36/62 encode and decode were about 9–18% below 4.x at this gate; alpha.1 includes the optimization
  (#1362). In the gate dry-run on the fix (smoke settings, run 40639407114; the formal gate before the RC is the
  conclusion), 4.x → 5.x ops/ms: radix36Decode 74,581 → 80,452 (+8%), radix62Decode 81,042 → 91,216 (+13%), radix36Encode
  49,452 → 64,265 (+30%), radix62Encode 53,439 → 70,299 (+32%). Allocation is no higher than 4.x (decode 0 B, encode 88 B
  vs 96–104 B).
- **MySQL store:** acquire, renew and reserve allocate about 25–67% more per call (acquire 50 KB → 63 KB, reserve
  8.6 KB → 14.4 KB); acquire's mean time is about 15% higher (1,541 → 1,768 µs), the other latencies 1–8% higher.
- **ZooKeeper store:** reserve allocates about 19% more per call (5.9 KB → 7.0 KB), renew about 2% more.
- **Segment (no prefetch):** 24 → 32 B allocated per id, single-thread throughput about 6% lower.
- **MongoDB store:** reserve allocates about 5% more per call, p99/p99.9 latency about 2–4% higher. **Redis store:** one
  reserve p99.9 row is high. Both are close to noise and will be rechecked.

Not affected, or better than 4.x: Snowflake generation (P1–P4), Spring startup, the Friendly codec, `IdFiller`, and the
other store rows.

These regressions will be fixed, or settled with data, before the RC.

The migration tool of this alpha refuses a 4.x CosIdGenerator with a `cosid.generator.namespace` of its own (GA review
R1-x-07): 4.x shares its machine ids across services, and this alpha has no shared machine for cosid80 yet. The next
release migrates it to the named machine `cosid.machines.generator`, with a slot offset above the 4.x machine ids so the
services can move one by one (D37, api-freeze.md §2.7).
